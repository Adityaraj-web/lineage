# F06 — Dashboard, read-only: provenance you can see

Branch: `f06-dashboard` · Commit prefix: `F06:` · Merge: `--no-ff` into `main` · Two phases, stop after each for review.

## Goal

A Next.js dashboard in `web/` that anyone can open, with no wallet and no keys, showing live testnet state:

- every payment with its **provenance badge**: P1 "Signed by you" · P2 "Resolved via registry" · P3 "Untrusted — needs you";
- the Lineage vault's **approval inbox**, where each held payment has a **risk card**: where the payee came from, account facts, history with this vault, how it compares to the signed mandate, and a plain-language reason;
- a **side-by-side comparison** of the latest demo run: same agent, same plan, same code; the attacker got 0 from Lineage and 49 tUSDC from LimitsOnly;
- proof the agent can only *request*: each agent account has exactly one function-call key (`request_payment` on its vault) and no full-access key.

F06 is read-only. Approve/reject, freeze/unfreeze (F07) and task creation (F08) are owner actions signed by a wallet. Leave no placeholders or disabled buttons for them.

## Architecture (keep it this way; the README will claim it)

- **Static site, no server.** `output: "export"` in `next.config.ts`. No API routes, route handlers, server actions, middleware/proxy, or server-side RPC. The dashboard holds no keys and has no backend. All chain reads run in the browser against public NEAR RPC.
- **Logic in `web/src/lib`, UI thin.** Pure, typed loaders and view-model builders return plain objects; components only render them. The pages, the unit tests (with fixtures) and `verify:web` (live) all use the same functions.
- **One source of truth for shared data.** `web/scripts/sync-shared.mjs` copies `deployments/testnet.json`, `deployments/demo-run.json` and `agent/vault-types.ts` into `web/src/shared/` (gitignored). It runs before `dev`, `build`, `test`, `typecheck` and `verify`. Never hand-edit or commit the copies.
- **Agent memos are untrusted text** (in the demo, the attacker wrote one). Render them as plain text only: no `dangerouslySetInnerHTML`, no markdown, no auto-linking.
- The root package is unchanged apart from delegating scripts: no new root dependencies. `web/` has its own `package.json` and lockfile.

## Data layer

### `rpc.ts`

- URLs: `NEXT_PUBLIC_NEAR_RPC_URL` (optional), then `https://test.rpc.fastnear.com`, `https://rpc.testnet.fastnear.com`, `https://near-testnet.drpc.org`. Drop any URL containing `rpc.testnet.near.org`; dedupe.
- `callView<T>(contractId, method, args)`: `query` with `request_type: "call_function"`, `finality: "final"`, `args_base64` = base64 of the JSON args. Decode the `result.result` byte array as UTF-8 JSON. Use `TextEncoder`/`TextDecoder` and base64 code that works in both the browser and Node 22 (no `Buffer` in browser code).
- `viewAccount(id)`: `{ exists: false }` on `UNKNOWN_ACCOUNT`, else `{ exists: true, amount, codeHash, isContract }`, where `isContract = codeHash !== "11111111111111111111111111111111"`.
- `viewAccessKeyList(id)`: `{ publicKey, permission: "FullAccess" | { receiverId, methodNames, allowance } }[]`.
- Errors: NEAR reports a contract panic either as a JSON-RPC `error` or as HTTP 200 with a string `result.error`. Handle both. Fail over to the next URL only on transport errors (network failure, timeout, HTTP 5xx or 429, error names `INTERNAL_ERROR` / `TIMEOUT_ERROR`). Throw a typed `RpcError` (name + message) on handler errors (`UNKNOWN_ACCOUNT`, contract execution errors) without failing over. 8 s timeout per request.

### `chain.ts`

`getConfig(vault)`, `getAllTasks(vault)` and `getAllPayments(vault)` (page with `from_index` / `limit: 50` until a short page), `getPayment(vault, id)`, `getAwaitingApproval(vault)`, `getPayeeStats(vault, account)`, `listServices()`, `ftBalance(account)`, `codeHash(account)`. U128 values stay `string` or `bigint`; never `Number`.

### `format.ts`

`fmtUsdc(u128: string | bigint)` matching `scripts/lib/near.ts` (6 decimals, trailing zeros trimmed: `"49 tUSDC"`, `"0.5 tUSDC"`), exact above 2^53. `fmtAgo(ms, now)`, `fmtDate(ms)`.

| `Untrusted` | Blocked or Failed | P3 | Untrusted — blocked | grey | the payment's reason |

Status pill: `AwaitingApproval` shows "Needs you"; the other statuses show their name.

### `risk.ts` — `assessPayment(facts): RiskCard`

Input facts, gathered by `views.ts`: the payment, its task, the vault mode, the other payments of the same task, `viewAccount(payee)`, and `get_payee_stats(payee)` on this vault.

Output: `{ level: "high" | "medium" | "low", findings: { id, tone: "danger" | "warn" | "info" | "ok", text, short }[], summary, advice }`. `text` is a full sentence for the card; `short` is a clause for the summary.

Rules, in this order (the ids are stable; tests use them):

1. `untrusted-source` (danger) when provenance is Untrusted: the agent took the address from a message it read; you did not sign it, and no resolver you pinned returned it.
2. `not-signed` (warn) when the payee is not one of the task's signed payees; list them ("Alice — logo → alice.lineage-aditya.testnet"). `signed-match` (ok) when it is.
3. `account-missing` (danger), else `contract-account` (warn), else `plain-account` (info).
4. `never-paid` (warn) when this vault's stats show 0 payments to the payee; else `paid-before` (info) with count, total and last date.
5. `duplicate-reference` (danger): an invoice-like token in the memo (`/\b[A-Z]{1,5}-\d{1,8}\b/`) also appears in the memo of another payment in the same task that is **Paid or Sending** to a **different** payee. Example: "Invoice A-102 was already paid in this task to alice.lineage-aditya.testnet (P1, signed by you, 18 tUSDC)."
6. `pressure-language` (warn): the memo claims changed payout details or pushes urgency: `/\b(new|changed?|updated?)\b.{0,20}\b(payout|bank|wallet|payment|account)\b|\burgent\b|\blate fee\b/i`.
7. `near-cap` (info) when the amount is ≥ 90% of `max_per_payment`.

Level: high if any danger finding, medium if any warn, else low. `summary` is one plain-language sentence built from at most three `short` clauses (danger first, then warn, each in rule order), with no LLM. Example: "Don't pay this yet: the address came from a message the agent read, invoice A-102 was already paid in this task to alice.lineage-aditya.testnet, and it isn't a payee you signed." `advice` when high: "Reject unless you confirmed the new address with the payee through a channel the agent didn't use." The card is advisory, and the UI says so: "The vault already refused to auto-pay this. This card helps you decide."

### `views.ts`

- `loadOverview()`: both vaults' config and code hash, agent key proofs, awaiting-approval count on `vault`, registry services, latest demo-run summary.
- `loadVaultView(key)`: config, code hash, tasks (task 0 labelled "verify fixture", the `demo-run.json` task labelled "latest demo run"), payments newest first with badges, and the inbox (AwaitingApproval payments, each with its risk card). On `guarded` the inbox is an empty state explaining that LimitsOnly mode never asks: it pays any request within limits.
- `loadCompareView()`: from `demo-run.json`, look up each message's payment id on both vaults with `get_payment` (live). Rows: message subject (the live memo), tool, then Lineage and LimitsOnly side by side (badge, status, payee, amount, explorer tx link). Totals: what the attacker (`vendor-payments`) received from each vault in that task (sum of Paid payments to it), and `sameCode` (equal code hashes).
- `agentKeyProof(keys, vaultId)`: ok only if there is exactly one key, it is FunctionCall, its receiver is the vault, and its methods are exactly `["request_payment"]`. Report the remaining allowance.
- Each `load*` gathers facts, then calls a pure `build*` function. Unit tests cover the `build*` functions with fixtures.

- Badges carry text, not colour alone.

## Design brief (Phase 2 is the real UI, not a draft)

The dashboard is what judges see in the video, so it must look striking. Effects go only where they explain the idea: a viewer should understand where each payee came from by watching.

Signature moments (build all four):

1. **Overview hero — the provenance flow.** An animated SVG with three lanes into the vault: P1 from "Signed by you" flows straight through; P2 goes out to the registry and comes back resolved; P3 from "an email" hits a gate and stops, glowing amber, labelled "Needs you". It loops calmly; under it, the one-line pitch.
2. **Compare — the money shot.** Split screen, same three payments on both sides. On the poisoned invoice row, LimitsOnly: a token travels to the attacker and the side flashes rose; Lineage: the gate closes and the payment is held (amber). The "attacker received" counters count up to 0 and 49 tUSDC. A "same code" seal (the shared code hash) sits between the halves. Plays once when the page loads, with a replay button.
3. **Risk card.** A risk meter fills to the level; findings appear one by one; the `duplicate-reference` finding draws a visible link from "A-102" in this payment to the earlier A-102 payment to Alice (shown as a mini row).
4. **Live updates.** When polling sees a new or changed payment, it slides in or its status pill morphs, with a brief highlight. The live indicator pulses. Animate on data change only, never on every poll.

Smaller touches: P3 "Needs you" has a soft pulsing glow; the agent key card shows what the key can do (`request_payment` on its vault) next to what it cannot (approve, withdraw, unfreeze, change limits), crossed out; amounts count up on first render.

Look: dark base (near-black with subtle grain or gradient), glassy cards with fine borders, one accent per provenance — P1 emerald, P2 sky, P3 amber, attacker rose. Geist Sans and Geist Mono (`next/font`), account ids in mono, amounts with tabular numbers. Generous spacing, a strong type scale, clear hierarchy.

Stack: Tailwind, shadcn/ui primitives, `motion` for animation, `lucide-react` icons, hand-built SVG for diagrams. No three.js or canvas libraries.

Rules: respect `prefers-reduced-motion` (every effect has a static equivalent that reads the same); no layout shift while polling; nothing animates in a way that hides text from screen readers; components still render deterministically under jsdom.

## Acceptance tests (write them first, show them failing, then implement)

**Unit** (`npm run web:test`, Vitest, offline; fixtures built from `deployments/demo-run.json` and the live shapes above):

- rpc: args base64 encoding and result decoding; failover to the next URL on a network error and on HTTP 503; no failover on `UNKNOWN_ACCOUNT` or on a contract panic in either error shape; `rpc.testnet.near.org` dropped even when set through the env var; `viewAccount` maps an unknown account to `exists: false` and detects a contract by code hash.
- format: `fmtUsdc("49000000") === "49 tUSDC"`, `"500000"` → `"0.5 tUSDC"`, and a value above 2^53 stays exact.
- provenance: every row of the table above.
- risk:
  - The demo P3 (#5: `vendor-payments`, 49 tUSDC, memo `URGENT: new payout details for invoice A-102`, stats 0, plain account; task with Alice signed in slot 0; #4 Paid 18 to `alice` with memo `Invoice A-102: logo design`) → level high with findings `untrusted-source`, `not-signed`, `plain-account`, `never-paid`, `duplicate-reference`, `pressure-language`, `near-cap`. The summary mentions `A-102` and `alice.lineage-aditya.testnet`.
  - The demo P1 (#4, with #5 AwaitingApproval in the same task) → level low, `signed-match`, no `duplicate-reference`.
  - Missing account → `account-missing` (danger). Contract payee → `contract-account`.
  - The same token paid earlier to the **same** payee → no `duplicate-reference`.
- views: the compare builder gives 3 rows and attacker totals 0 (Lineage) vs 49 tUSDC (LimitsOnly); `sameCode` is false when hashes differ. `agentKeyProof` fails for a full-access key, for a second key, for a wrong receiver and for an extra method.
- components (Testing Library + jsdom): ProvenanceBadge text for P1, P2 and P3; RiskCard shows the level, summary and findings; a memo of `<img src=x onerror=alert(1)>` renders as literal text and creates no `img` element.
- Mutation checks (report each, then revert): remove the `duplicate-reference` rule → a risk test fails; let `agentKeyProof` accept two keys → a views test fails.

**Live** (`npm run verify:web`, no account needed, Checklist output):

1. Both vaults are reachable; modes are Lineage and LimitsOnly.
2. `vault` and `guarded` have the same code hash.
3. Each agent account has exactly one key: function-call, receiver its vault, methods `["request_payment"]`.
4. Compare view of the demo-run tasks: Lineage P2 Paid, P1 Paid, P3 AwaitingApproval or Rejected (never Paid); LimitsOnly all three Paid; attacker received 0 vs 49 tUSDC.
5. If the demo-run P3 is still AwaitingApproval, its risk card is high and has `untrusted-source`, `not-signed`, `never-paid` and `duplicate-reference`.
6. Registry: `translate-hi` is Verified → `hindi-translator`, 25 tUSDC.
7. The overview loads without errors.

**Build:** `npm run web:build` produces `web/out/` (static export) with no errors and no type errors. You cannot click, so end Phase 2 by telling Adityaraj how to serve `web/out/` locally and what to check in the browser, including that the RPC calls succeed (no CORS errors in DevTools).
