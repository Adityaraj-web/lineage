# F07 — Owner actions, signed by the owner's wallet

Branch: `f07-owner-actions` · Commit prefix: `F07:` · Merge: `--no-ff` into `main` · Four phases, stop after each for review.

## Goal

The dashboard stays a static site with no keys, but the **owner** can now act from it with their own wallet:

- **Connect** a NEAR wallet through NEAR Connect (testnet). Anyone can connect. Controls appear only when the connected account **is the vault's owner** (`account === get_config().owner`). Everyone else is a **Viewer** and sees exactly what F06 showed, plus one line saying who they are connected as.
- **Approve / Reject** on each inbox card (Lineage vault, payments `AwaitingApproval`). Approving a **high-risk** payment needs a tick: "I confirmed this address with the payee outside this conversation." Reject opens with a prefilled reason the owner can edit.
- **Freeze / Unfreeze** switch on both vaults (`vault` and `guarded`).
- After each action: the tx hash, an explorer link, and a refresh so the change shows within one render cycle (not after the next 5 s poll).

The contract is the guarantee and does not change in F07. The UI only builds and sends calls the contract already checks: owner only, exactly 1 yocto for everything except `freeze`.

## Architecture (keep it this way; the README will claim it)

- **Still static, still no keys.** `output: "export"`, no API routes, no server, no env secrets. Keys stay in the user's wallet. The site never sees one.
- **Wallet code is isolated.** `@hot-labs/near-connect` (pin `0.12.0`, zero dependencies; do **not** add near-api-js or the deprecated `@near-wallet-selector/*` to `web/`) is imported **only** in `web/src/components/wallet/connector.ts`, and only through `await import(...)` inside a client effect. It touches `window`, `localStorage` and IndexedDB, so a top-level import breaks `next build` or pre-renders a wrong state.
- **Everything else depends on a small interface**, so components and tests never need the real library:
  ```ts
  // web/src/lib/wallet.ts
  export interface WalletPort {
    accountId: string | null;               // null = not connected
    connect(): Promise<void>;
    disconnect(): Promise<void>;
    send(tx: OwnerTx): Promise<unknown>;     // raw outcome; parse with parseOutcome
  }
  ```
- **Action builders are pure and exact.** `web/src/lib/actions.ts` returns plain objects in the NEAR Connect `ConnectorAction` shape. No component builds args, gas or deposit itself.
- **Owner check is a view, not a guess.** Owner = `get_config().owner` of that vault, already loaded by `loadVaultView`. No hard-coded root id in components.
- **Untrusted text stays text.** Memos, payee ids and the owner's own reject reason render as React text nodes only.

## Phase 1 — Pure logic (tests first)

### `actions.ts`

```ts
export const ONE_YOCTO = "1";
export const GAS = { approve: "100000000000000", reject: "30000000000000", freeze: "30000000000000", unfreeze: "30000000000000" } as const;
export interface OwnerTx { receiverId: string; actions: [FunctionCallAction] }   // exactly one action
export function approveTx(vault: string, paymentId: number): OwnerTx;
export function rejectTx(vault: string, paymentId: number, reason: string): OwnerTx;
export function freezeTx(vault: string): OwnerTx;
export function unfreezeTx(vault: string): OwnerTx;
export const REJECT_REASON_MAX = 140;
export function defaultRejectReason(risk: RiskCard): string;
```

- Each returns `{ receiverId: vault, actions: [{ type: "FunctionCall", params: { methodName, args, gas, deposit } }] }`. Amounts are decimal strings, never numbers.
- Args exactly: approve `{ payment_id }`, reject `{ payment_id, reason }`, freeze `{}`, unfreeze `{}`. `payment_id` is a non-negative integer; throw on anything else (NaN, negative, fractional).
- Deposits exactly: approve, reject, unfreeze `"1"`; freeze `"0"`.
- Gas: approve 100 Tgas (it chains `storage_deposit` → `ft_transfer` → callback, 40 Tgas of static gas plus overhead); the rest 30 Tgas, matching `agent/owner.ts`.
- `rejectTx` trims the reason, cuts it to `REJECT_REASON_MAX` characters on a code-point boundary (`Array.from`), and sends `"Rejected by owner"` if it ends up empty.
- `defaultRejectReason`: high risk → `"Payee not in the signed mandate; payout change not confirmed with the payee"`; otherwise `"Not approved by owner"`. Keep it short and factual. It is stored on-chain and shown publicly.

### `tx.ts`

`parseOutcome(raw: unknown): { hash: string | null; ok: boolean; error: string | null }`

- `hash` from `transaction.hash`, else `transaction_outcome.id`, else `null`.
- `ok` = `status` has `SuccessValue` (string, may be `""`) **and** no `receipts_outcome[i].outcome.status.Failure`.
- `error` = a short readable line from the first `Failure` found (prefer `ActionError.kind.FunctionCallError.ExecutionError`, e.g. `"Smart contract panicked: Owner only"`), else `null`.
- Unknown shape (some wallets return less) → `{ hash, ok: true, error: null }` when a hash exists, so the UI says "Submitted" and links the explorer. The refresh shows the real result.
- Also export `walletErrorMessage(e: unknown): string`: user closed or rejected the wallet → `"Cancelled in the wallet"`; anything else → the error's message, cut to 160 chars.

### `wallet.ts`

`type Role = "disconnected" | "viewer" | "owner"`; `roleFor(accountId: string | null, owner: string | null): Role`. Owner match is exact string equality (NEAR ids are lowercase; do not lower-case or trim to make a match).

### Acceptance tests (Phase 1)

- Every builder: exact `receiverId`, method name, args object (`toStrictEqual`), gas and deposit strings.
- **Mutation check (required):** temporarily change `approveTx`'s deposit to `"0"` and show at least one test failing; same for `unfreezeTx`; same for `freezeTx` with `"1"`. Revert, show green. Paste the three red runs in the phase report.
- `approveTx(v, -1)`, `approveTx(v, 1.5)`, `approveTx(v, NaN)` throw.
- `rejectTx`: whitespace-only → `"Rejected by owner"`; a 200-char reason with emoji at the cut → 140 code points, no lone surrogate.
- `parseOutcome`: success fixture; top-level `Failure` fixture (`Owner only`); success at the top but a failed receipt → `ok: false`; hash-only shape → `ok: true`; garbage → `hash: null`.
- `roleFor`: null account → disconnected; owner → owner; `"Lineage-aditya.testnet"` → viewer.

## Phase 2 — Wallet connection and roles

### `connector.ts`

- `createConnector()` does `const { NearConnector } = await import("@hot-labs/near-connect")`, then `new NearConnector({ network: "testnet" })`. No `addFunctionCallKey` on connect: we never want a function-call key added to the owner account, and it could not attach the 1 yocto anyway.
- Adapts the connector to `WalletPort`: `connect()` opens the wallet picker; `send(tx)` gets the connected wallet and calls `signAndSendTransaction({ receiverId, actions, signerId: accountId })`; listens to `wallet:signIn` / `wallet:signOut` and pushes account changes to the provider.
- Wallet-agnostic: no wallet id hard-coded, no wallet filter except network testnet.

### `WalletProvider.tsx`

- Lives in `Providers.tsx`. On mount (client only) creates the connector, awaits `whenManifestLoaded`, then `getConnectedWallet()` to restore a session silently. If that throws (none), the state is `disconnected`.
- Exposes `{ port, status: "loading" | "ready" | "unavailable" }`. If the dynamic import or manifest load fails (offline, blocked), status is `unavailable`: the Connect button is hidden and the site works exactly as F06. A wallet failure never breaks reading.
- Server render and first client render are identical (`loading`, no button), so there is no hydration mismatch.

### `ConnectButton.tsx` (in `Nav`)

- Disconnected: a quiet "Connect wallet" chip in the nav (Glass chip; no new glass tier).
- Connected: `AccountId` of the account (truncated, mono) + a menu with "Disconnect". Do not show the role in the nav (the role is per vault; the vault page shows it).
- Keyboard and screen reader friendly: real `button`s, `aria-expanded` on the menu, focus returns to the trigger.

### Role on the vault page

- `VaultScreen` reads the port, computes `roleFor(port.accountId, view.config.owner)`, passes `role`, `onAction` (a `useOwnerAction` bound to this vault) and the polling `refresh` down to `VaultDashboard`.
- Viewer (connected, not owner): one muted line under the vault header: "Connected as `<id>`. Only the owner `<owner>` can act on this vault." No disabled buttons anywhere.
- Disconnected: nothing new at all (F06 page exactly).

### `useOwnerAction`

State machine, one action at a time per page:

`idle → signing (wallet open) → submitted → done { hash, ok, error }` or `→ failed { message }`.

- While `signing` or `submitted`, every owner control on the page is disabled and the one in flight shows "Waiting for your wallet…" / "Sending…".
- On `done` or `failed`: show `TxResult` in place (hash as `AccountId`-style mono, explorer link via `explorerTx`, error line if any), then call `refresh()` immediately and once more after 2 s (approve settles in a later block through the callback; the first read may still say `Sending`).
- `done` with `ok: false` is shown as failed with the contract's message (e.g. "Payment is not awaiting approval" if someone else already acted).
- Results clear on the next action or after the item leaves the inbox.

## Phase 3 — Controls (real UI, not a draft)

### `OwnerActions` on each inbox card (owner only)

Placed at the foot of the risk column, under the risk card, inside the same Glass card (no new blurred panel).

- **Reject is the primary button** (it is the safe default for a held payment). **Approve is secondary.** On high risk, Approve uses the attacker tone outline, never a filled green.
- Approve first expands an inline confirm, not a modal: "Pay **49 tUSDC** to `vendor-payments.lineage-aditya.testnet` from task 2." Amount and payee come from the payment row (`row.amount`, `payment.payee`), never from the memo.
  - High risk: a checkbox "I confirmed this address with the payee outside this conversation." The confirm button stays disabled until it is ticked. Medium/low: no checkbox.
  - Buttons: "Approve and sign" / "Back".
- Reject expands an inline field prefilled with `defaultRejectReason(risk)`, a character count against 140, and "Reject and sign" / "Back".
- Copy under both: "Your wallet will ask you to confirm. It needs a full-access key on the owner account." (one muted line).
- After a successful action the card leaves the inbox through the existing `AnimatePresence` exit; its `TxResult` moves to a small "Last action" line at the top of the inbox section (so the hash stays visible after the card is gone).

### `FreezeSwitch` in `VaultHeader` (owner only, both vaults)

- A switch with the existing Active / Frozen status. Off → on calls `freezeTx`; on → off calls `unfreezeTx`.
- Freeze needs no confirm (it is the safe direction). Unfreeze expands a one-line confirm: "Unfreeze? The agent can spend again within its caps."
- Short help text: "Freeze stops every payment, including signed ones. Any owner key can freeze; unfreezing needs a full-access key."
- The switch shows the chain's value only: it does not flip until the refresh confirms the new `frozen` value (no optimistic state).

### Design

Match F06: Glass chip/card only, Plus Jakarta Sans for labels and numbers, JetBrains Mono for ids and hashes, `.chip-ink` for small coloured text on tints, contrast checked on the real backdrop. Focus rings visible. Reduced motion: no expand animation, instant swap. Mobile (390 px): buttons stack full-width, the confirm text wraps without truncating the payee id.

### Tests (Phase 3)

- Owner, high-risk item: Approve → confirm shows exact amount and full payee id; "Approve and sign" disabled until the checkbox is ticked; clicking it calls `FakeWallet.send` with `toStrictEqual(approveTx(vault, 5))`.
- Owner, medium-risk fixture: no checkbox; confirm enabled.
- Reject: field prefilled with the high-risk reason; edited reason is sent through `rejectTx` (trimmed, capped).
- Freeze switch: freeze sends `freezeTx` (deposit "0"); unfreeze asks to confirm, then sends `unfreezeTx` (deposit "1").
- While one action is `signing`, every other owner button is disabled.
- Wallet rejection → "Cancelled in the wallet", controls enabled again, no refresh storm (refresh called at most twice).
- A memo containing `<img src=x onerror=alert(1)>` still renders as text in the confirm view (extend the existing XSS test).
- All existing tests stay green (≈195 + new).

## Phase 4 — Owner wallet setup, docs, rehearsal

### `docs/owner-wallet.md` (Adityaraj runs every command; Claude Code does not sign)

**Add a dedicated full-access key for Meteor (testnet)**. The legacy-keychain root key is never exported.

```bash
near account add-key lineage-aditya.testnet \
  grant-full-access autogenerate-new-keypair print-to-terminal \
  network-config testnet sign-with-legacy-keychain send
```

- It prints a seed phrase and the new public key. Write the public key into `docs/owner-wallet.md` (public keys are safe to commit). Import the seed phrase in Meteor (testnet → Import → seed phrase). Then `clear` the terminal; never paste the phrase anywhere else.
- Check: `near account list-keys lineage-aditya.testnet network-config testnet now` shows the old key plus the new one, both full access.
- If `near` prompts interactively instead (subcommand names differ in this version), follow the prompts with the same choices; `near account add-key --help` lists them.

**Remove it after the hackathon (one command):**

```bash
near account delete-keys lineage-aditya.testnet \
  public-keys ed25519:<METEOR_PUBLIC_KEY> \
  network-config testnet sign-with-legacy-keychain send
```

Then `list-keys` again: only the original key remains.

**Alternative for README readers:** choose "NEAR CLI" in the NEAR Connect picker. It signs with near-cli-rs on your machine, so the key never leaves your keychain.
